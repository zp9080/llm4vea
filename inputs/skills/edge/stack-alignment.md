# 适用场景
栈对齐是 x86-64 架构下进行 ROP 攻击时一个常见但易被忽略的问题。当你构造的 ROP 链在调用某些 libc 函数（特别是 `system`, `printf`, `execve` 等）时，无明显原因地发生段错误（`SIGSEGV`），且 GDB 调试显示崩溃发生在函数序言的 `movaps` 或类似的 SSE 指令上，那么极有可能是栈对齐问题。

# 原理分析
- **x86-64 System ABI 规约**:
  - **核心要求**: 在执行 `call` 指令**之前**，栈指针 `rsp` 的值必须是 16 字节对齐的。也就是说，`rsp` 的地址末尾应为 `0`。
  - **原因**: 许多现代 libc 函数使用 SSE 指令集（如 `movaps`）进行优化，这些指令要求操作的内存地址是 16 字节对齐的。如果 `call` 时栈没有对齐，那么函数序言中对栈的操作（如 `push rbp`）会破坏后续 SSE 指令所需的对齐，导致程序崩溃。

- **ROP 链如何破坏对齐**:
  - `call` 指令会隐式地将返回地址（8 字节）压栈，使 `rsp` 减少 8。
  - 函数序言 `push rbp` 会使 `rsp` 再减少 8。
  - ROP 链中的每个 `ret` 指令都会 `pop` 一个地址（8 字节）到 `rip`，使 `rsp` 增加 8。
  - 如果你的 ROP 链在 `call <target_func>` 之前，`ret` 的次数是奇数次，那么相对于初始对齐状态，`rsp` 的对齐状态就会被破坏。

# 解决方法
- **利用路径 (修复方法)**:
  - **增加一个 `ret` Gadget**: 这是最简单、最通用的修复方法。在调用目标函数（如 `system`）之前，在 ROP 链中额外插入一个 `ret` gadget 的地址。
    - **效果**: 这个额外的 `ret` 会从栈上弹出一个值（我们可忽略其内容），使 `rsp` 增加 8 字节。这个操作恰好可以修正因 `call` 指令压栈返回地址而导致的 8 字节偏移，从而恢复 16 字节对齐。
  - **payload 示例**:
    - **错误**: `[padding] + [pop_rdi_ret] + [bin_sh_addr] + [system_addr]`
    - **正确**: `[padding] + [ret_gadget] + [pop_rdi_ret] + [bin_sh_addr] + [system_addr]` (如果初始状态下 `call` 之前是对齐的)
